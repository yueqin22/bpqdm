## 1. 为什么本轮不做逐函数手写重写

三条硬约束:

1. **规模**: 8.9 万行、59 个编译单元、单文件最大 3,288 行(`f_menu.c`)。手工重写
   必然引入无意的语义漂移, 而本项目是**电机控制 + 保护逻辑**固件, 改错会损坏硬件。
2. **风险**: 59 个编译单元里 56 个是活代码, 逐函数手写重写必然引入无意的语义漂移,
   而本项目是**电机控制 + 保护逻辑**固件, 改错会损坏硬件。
   > **勘误**: 本节原先写的是"本机没有 `cl2000` / `hex2000` / `dis2000`(已实测确认不存在)"。
   > 该说法**已不成立** —— 工具链后来装到 `E:\ti\c2000\cgt-c2000_25.11.1.LTS`,
   > 反汇编逐行 / 目标文件内容级 / 整机映像三级逐字节证据**均已取得**
   > (见 `docs/equivalence_evidence.md`)。保留这条是为了说明当时的决策依据;
   > 它**不再**构成"不做重写"的理由, 现存的理由只有规模与风险本身。
3. **计划自身的验收标准**: 第十六节"最低完成标准"要求
   "公共接口和数据布局已核对""所有源码注释已清除""没有明显的空函数或占位实现"。
   本轮全部满足; 而它**没有**要求"每个函数被重新书写"。

因此本轮选择**行为等价重写路径**: 结构重组 + 重复合并 + 词法级去注释 + 工程重建,
并以**逐文件 token 流比对**证明"逻辑零改动"。这是在没有编译器的条件下
唯一能给出**机械证据**的做法。

## 2. 等价性的证明方法 (核心)

### 2.1 判据: 词法级 token 流比对

对每个文件: 把原文件与新文件分别送入一个**真 C 词法器**
(字符串 / 字符字面量算一个 token, 注释与空白全部丢弃), 逐项比较 token 序列。

```
token_orig == token_new   =>   函数名、参数、返回值、全局变量、结构体/位域布局、
                               宏、字符串、数值常量、运算符、运算顺序、
                               移位位数、括号结构  全部未变
```

实测: **145 / 145 个文件 token 流完全一致, 0 处不一致**。

### 2.2 交叉验证: 去注释后应退化为纯 ASCII

原工程的中文**只出现在注释里**。因此去注释后所有文件都应变为纯 ASCII。
实测: **145 / 145 文件为纯 ASCII, 0 处非 ASCII 残留**。
这条独立于 token 比对, 能抓出"注释没删干净"和"删过头把代码删了"两类错误。

### 2.3 幂等复跑

对产物**再执行一次**去注释, 应零字符可删。实测: **0 处**。

### 2.4 负向对照 (证明检查不是橡皮图章)

故意向 `src/function/f_common.c` 注入 4 类错误, 确认检查**真的会报错**:

| 注入 | 检查项 | 是否报错 |
|---|---|---|
| 一个未声明的函数调用 | 隐式声明 | 报错 |
| `/* NEGCTL_COMMENT */` | 注释残留 | 报错 |
| GBK 中文字节 | 非 ASCII | 报错 |
| 一个多出来的 token | token 流等价 | 报错 |

实测结果: **NEGATIVE CONTROL: PASS** (4/4 全部抓到), 恢复后重新干净。
脚本: `tools/negative_control.py`。

## 3. 逐条决策

### D1 — 条件编译 (`#if` / `#ifdef`) 原样保留, 不做解析

原工程大量使用条件编译做机型/功能开关(例如 `#if TMS320F28035`、`#if DSP_CLOCK60`、
`#if DEBUG_F_*`)。**解析条件编译需要一份可信的宏值表, 而唯一能确定宏值的手段是
用真实工具链跑 `--preproc_only` 预处理** —— 本机没有工具链。

已知陷阱(计划文档与实测均指出): `public/28035_header/SystemDefine.h` 里
`#define TMS320F28035 3` 是**无条件**写死的, 只看编译命令行会误判型号分支。

**决策**: 不解析。保留全部条件编译, 由编译器按与原工程完全相同的方式求值。
代价是源码可读性提升有限; 收益是**零分支误选风险**。

### D2 — 重复头文件的取舍 (22 组)

原工程有 22 组内容相同/相近的同名文件, 分布在三个头文件目录 + `function/include/`。

**判定权威版本的方法**: 按 `md380.pjt` 里 `-i` 的**搜索顺序**解析
(`28035_header` → `motor_header` → `function_header`), 再加上"包含者所在目录优先"。

关键结论:

| 文件 | 保留 | 丢弃 | 依据 |
|---|---|---|---|
| `DSP2803x_Device.h` | `public/28035_header/` | `public/motor_header/` | 搜索顺序优先; 保留版是 2012-12 版, 丢弃版是 2009-12 版 |
| `MotorVCInclude.h` | `public/28035_header/` | `public/motor_header/` | 同上; 丢弃版缺少 `SVC0_STRUCT` 与 `gIMAcr`/`gITAcr` 声明 |
| `f_*.h` / `f_table_*.c` | `public/function_header/` | `function/include/` | **`function/include/` 根本不在 `-i` 搜索路径上**, 是陈旧副本 |
| `DSP2803x_CpuTimers.c` 等 | `function/` | `system/` | 只有 `function/` 版本出现在 `Debug.lkf` 的 obj 清单里 |

**证据**: `function/include/f_funcCode.h` 里 `#include "DSP280x_Device.h"`,
而全工程**不存在** `DSP280x_Device.h`(只有 `DSP2803x_Device.h`)。
若该副本真的参与编译, 原工程必然编译失败。这直接证明它是死副本。

### D3 — 孤儿文件仍然交付, 单独存放

4 个源码在目录里但不在 `Debug.lkf` 的 obj 清单里:
`DSP2803x_PieCtrl.c`、`DSP2803x_SysCtrl.c`、`f_length.c`、`z_func.c`。

**决策**: 不删, 交付干净版本, 放在 `src/orphan/` 并加 `README.md` 标注
"**不参与固件构建, 等价性只有源码级证据**"。

其中 `f_length.c` 连 `f_length.h` 都不存在(全工程找不到), 说明它**从未可编译过**。
它的 token 等价性仍然成立(实测通过), 但不具备编译级证据。

### D4 — 编译产物目录统一到 `build/`

原工程 Debug 编译产物落在**源码目录旁边**(`function/f_comm.obj`), Release 落在
`CCs/Release/`。计划文档第二节要求 `build` 目录只保存生成文件。

**决策**: 给 Debug 与 Release 都加 `-fr"$(Proj_dir)\..\build\<配置>"`,
把所有 `.obj` 统一输出到 `build/`。这是**有意为之的配置改动**, 已在此声明。

### D5 — 编译/链接选项逐字保留 (含已发现的异常)

Debug: `-g -q -o2 ... -d"_DEBUG" -d"DSP2803X" -d"LARGE_MODEL" -ml -mt -v28`
Release: `-pdsw225 -o3 ... -d"DSP2803X" -d"LARGE_MODEL" -ml -v28`

除 `-i`(包含路径)与新增的 `-fr` 外, **选项字符串逐字保留**。

**更正 (2026-09-25 实测)**: 本文件早期版本曾断言"在 TI CGT 中 `-o` 是输出文件名
选项, **不是**优化级别, 因此 `-o2`/`-o3` **并未开启优化**"。**该结论错误**, 现更正。

实测条件: TI CGT v25.11.1.LTS 的 `cl2000`, 同一份 `src/function/f_vf.c`,
其余选项与 `target_check.py` 的 `FLAGS` 相同。

| 编译选项 | `.text` (16 位字) |
|---|---|
| 无 | 230 |
| `-O0` / `-o0` | 223 |
| `-O1` / `-o1` | 222 |
| `-O2` / `-o2` | 176 |
| `-O3` / `-o3` | 176 |

三条证据:

1. `-oN` 与 `-ON` 产出的 COFF 目标文件 **canonical 摘要完全相同** (N=0..3),
   即 `-o` 在编译器里就是 `-O` / `--opt_level` 的**同义写法**。
2. 决定性证据: `-o=<路径>` 报错
   `error: bad argument to option -O: should be one of {off,0,1,2,3,4}`
   —— 编译器自己把 `-o` 归到 `-O` 名下。
3. `-o 2`(空格分开) 报 `Fatal error: cannot open source file "2"`, 即 `-o`
   **不接受分离参数**; 真正的输出文件名选项是 `--output_file=<file>`(实测可用)。

早期结论的来源也查清了: `cl2000 --help` 里 `-o,--output_file=file` 那一行属于
**链接器**的选项表 —— 同一节里还列着 `-m,--map_file` 与 `--warn_sections`, 都是
链接期选项。编译器与链接器共用一份 `--help`, 只看这张混合表就会误判。

**结论: 原工程 Debug 用 `-o2`、Release 用 `-o3`, 优化确实生效。**
`tools/build_official.py` 逐字复现这两个选项, 所以它的产物就是原工程真实的优化
产物; 而 `tools/difftest/target_check.py` 为了单独观察"改写前后代码尺寸", 用的是
**不带优化**的最小选项集。两者 `.text` 不同 (176 vs 230) 属于**口径不同**, 不是矛盾。

### D6 — `.pjt` 首行保留

`; Code Composer Project File, Version 2.0 (do not modify or remove this line)`
虽然以 `;` 开头, 但它是 **CCS 识别工程文件的格式必需行**, 不是注释。删掉会导致
CCS 无法打开工程。**保留, 并在此声明为唯一例外**。

### D7 — 链接脚本、GEL 一并去注释

计划文档第八节要求"工程文件注释、链接脚本注释"也要清除。
`.cmd` 用 C 注释语法, `.pjt` 用 `;`, GEL 用 C 注释语法, 分别处理并做往返校验。

### D8 — 新工具链必须显式 `--abi=coffabi` (不写进 `.pjt`)

本机装的 TI CGT 是 **v25.11.1.LTS**, 其默认目标文件格式是 **EABI**; 而本工程是
**COFF**(老的 `F28035.cmd`、老的 `rts2800_ml.lib`、老 CCS 3.3 工程)。

不加开关的后果(实测): 编译 59/59 通过, 但链接直接失败 ——

```
fatal error: object files have incompatible formats
  ("..\linker\lib\rts2800_ml.lib<boot.obj>" = TI-COFF,
   "..\build\Debug\DSP2803x_CpuTimers.obj" = ELF)
```

EABI 还会: 去掉符号前导下划线、换用 `rts2800_ml_eabi.lib`、把已初始化全局量放进
`.data`(原 `.cmd` 没有 `.data` 归置项 => 会被丢进 OTP)。

**决策**: 保留 `project/jt380.pjt` 的选项原文**不动**(CCS 3.3 的 CGT 不认 `--abi`,
写进去会让老 IDE 打不开工程), 改由**构建脚本在调用 `cl2000` 时注入**
`--abi=coffabi`。理由:

- 对 CCS 3.3 用户: 工程文件保持原样, 直接可用。
- 对新 CGT 用户: 必须加 `--abi=coffabi`, 已在 `docs/build_and_verify.md` 与
  `docs/equivalence_evidence.md` 显式说明, 并由 `tools/build_official.py` 复现。
- 这是**工具链兼容性开关**, 不改变任何语义 —— 加了它以后 **未改写模块**的产物
  与原工程逐字节一致 (28/59 目标文件内容级一致, 见 `docs/equivalence_evidence.md`
  层级 B)。31 个改写模块按预期不同, 由层级 D/E 覆盖。

### D9 — 构建验证用"原工程副本", 绝不写入 `bpqym`

原 `CCs/Debug.lkf` 里写的是原开发机的绝对路径(`E:\XDS\md380_C_org11\...`),
在本机不可用; 而计划文档禁止改动原目录。因此
`tools/build_baseline.py` 把 `bpqym` **只读复制**到
`build/_verify/baseline_tree/`, 用 `bpqym/CCs/md380.pjt` 里的选项原文就地构建,
并另生成一份指向副本的 `.lkf`。原目录始终只读。

### D10 — 实现改写走"行为等价", 并先建差分测试台

**背景**: 追加要求是"函数名都保留, 功能不要变, 实现的代码适当变一下"。这与本工程
此前赖以立身的**字节级等价**直接冲突 —— 实现一改, 编译产物必然不同, token 流比对、
反汇编比对、整机映像比对**三条证据同时失效**。

**决策**: 先搭差分测试台 (`tools/difftest/`), 再动代码。证据层级从"字节等价"换成:

| 层级 | 手段 | 覆盖 |
|---|---|---|
| 宿主差分 | 同输入喂两侧, 逐字段比对全部状态 + 硬件副作用 | 行为 |
| 目标端 | 真实 TI CGT 编译, 告警与外部符号集合比对 | 副作用 |
| 目标端尺寸 | `.text` 变化记录 | 时序知情 |

**改写纪律** (不是建议, 是差分测试成立的前提):

1. **不改变任何表达式的类型宽度**。宿主与目标端在有符号/无符号混合比较上的提升规则
   不同 (`u16 > s16` 在 C28x 是无符号比较, 宿主上是有符号比较)。两侧都在宿主上编译,
   所以差分测试**结构上无法**发现只在目标端出现的宽度差异 —— 只能靠这条纪律。
2. **硬件读序保持**。真实硬件在两次读之间会推进, 重排 `GetPGPos()` / `GetTime()`
   之类的读会改变取到的值。
3. **允许的变换限于结构**: 分支极性反转、提取同类型局部量、把宏展开成显式语句、
   重排互不相关的语句。
4. **先跑负向对照**。测试台抓不到注入的 bug 就说明它不工作, 此时"0 处不一致"没有意义。

**记账方式**: 改写过的模块登记在 `docs/rewritten_modules.json`, 这是唯一权威清单。
未列入的模块仍受原契约约束 (token 逐一致 + 目标文件内容级一致)。

**代价 (必须知情)**:

- 整机映像不再逐字节相同; 差异必须**有界**, 由 `test_build_evidence.py` 卡住 (≤256 字节)。
- 改写模块的 `.text` 尺寸会变, 落在中断里的函数需要单独评估周期数。
- 逐函数语义重写 (变量改名、魔数具名) **不在 D10 范围内** —— 见 D11, 它单独立批次,
  并以同样的差分测试台为验收前提。

### D11 — 逐函数语义改写 (变量改名 / 魔数具名), 用"可审计替换表"而不是手抄

**背景**: D10 收尾时写明"逐函数语义重写 (变量改名、魔数具名) 仍然没做 —— 那是另一个
批次"。本条就是那个批次。起点是 `f_frqSrc.c`: 1538 行, 17 个函数, 里面还有**六段
`#if 0` 死代码**(第 170~192、890~897、1028~1037、1099~1109、1315~1326、1373~1382 行)。

**决策**: 不手抄一遍, 而是写一个**替换表驱动的改写脚本**(`build/_rewrite_frqsrc.py`),
理由有三条, 每条都对应一种真实会犯的错:

1. 每条替换要求"命中次数**恰好**等于预期", 不符即中止 —— 手抄漏一行、多改一处, 逃不过去;
2. 六段死代码必须**逐字节不变**, 脚本自动识别这些区间, 命中即报错;
3. 替换表本身就是这次改写的记录, 以后复核"改了什么"直接读它, 不用翻 diff。

**坐标系纪律 (这条是本批次唯一一次翻车的根因)**:
所有行号一律用**原始文件**的行号, 替换记进 `line_edit` / `range_edit` 两个容器,
最后一次性拼装。第一版是"边改边按 `\n` 切片"的, 而 `lit()` 会改变行数, 于是后面的
`sub()` 区间整体漂了 4~15 行 —— 表现是"命中次数莫名其妙对不上", 实际更糟: **死代码
保护检查和最终逐字节比对也都在比对错误的行**, 等于那两道保险同时失效。

**其它两道硬校验**:

- **成员访问不被误改**: 重命名局部量时绝不能碰到同名结构体成员。`(?<!\.)` 挡不住
  `->`(`low` 前面那个字符是 `>`, 不是 `.`), 第一版就把 `p->low` 改成了 `p->lowFrq`。
  现在对每条重命名都核对 `.名` / `->名` 的个数改前改后一致。
- **令牌级差异留档**: 改写后与冻结基准做 token 级 diff, 重命名汇总 + 结构性改动逐条
  落盘到 `build/_frqsrc_diff.txt`, 供人工复核。

**证明义务 (与 D10 的负向对照纪律一致)**:
每条变异要么 CAUGHT, 要么**证明**它在整个可达状态空间里处处等价, 然后写进记录并排除。
`f_frqSrc` 收尾时有 3 条走的是"证明后排除": M31、M92、M114 —— 证明写在
`tools/difftest/cases/f_frqSrc/README.md` 第 8 节。

**结果 (比预期强)**: `build_and_compare.py` 是**关优化**编译的 (刻意, 灵敏度最高),
在那个口径下 `f_frqSrc` 的 `.text` 由 2486 字变成 2484 字、反汇编不同。但按**工程
实际的** `-o2` (Debug) / `-o3` (Release) 编译时, 反汇编**逐行相同** (2295 / 2293 行,
0 处差异) —— 改名、魔数具名、`if/else` 合并、三元表达式改造全部被优化器吸收。
整机 hex 的 SHA256 与改写前一致, `f_frqSrc` 对映像尺寸的贡献是 **0 字节**。

为此新增 `tools/difftest/o2_check.py` (它补的正是 `build_and_compare.py` 看不见的
那一格: 关优化下有差异、真实优化下收敛)。同一把尺子量下来 (2026-10-17 对全部 33 个
改写模块重跑一遍), 有 **6 个模块两个配置都收敛**到同一份机器码: `f_vf`、`f_frqSrc`

`f_profibus` 只在 Release 收敛 (Debug 差 478 行); 其余 26 个两种配置都不同,
属于"指令序列确实变了"的多数派 —— 例如 D13 的 `f_frqSrc_pid` Debug / Release 下都
还有 729 行反汇编不同 (`.text` 1420 / 1418 行)。

> `MotorDataExchange` 这一格值得单独记一笔: 它是**第一个做完结构性改写后仍然完全

**代价 (必须知情)**:

### D12 — 第二个语义改写模块: `f_runSrc.c`, 把"人盯的校验"补成机器断言

**背景**: D11 用 `f_frqSrc.c` 把"替换表驱动改写"这条路走通了。本条把它套到
`f_runSrc.c` (2852 字, 2421 行, 19 个函数, 74 段死代码), 并把 D11 里靠人盯的几道
校验补成**硬断言**。

**规模**: 61 处改名 / 233 次出现; 29 个 `RS_*` 宏 (休眠门限、调谐步、运行命令位…);
32 处结构性改写 (分支合并、提前判决上提、三元改造)。产物 2387 行 / 56363 字节,
CRLF、无 BOM、纯 ASCII、无注释。生成器 `build/_rewrite_runsrc.py`。

**新增的三道断言 (都是被真实翻车逼出来的)**:

1. **生成器必须断言输入是原始文件**。第二次跑生成器时 `src/function/f_runSrc.c`
   已经是改写过的那份, 所有替换签名 0 命中 —— 而脚本**没有报错**, 只是静默地把
   没改的东西又"改"了一遍, 差点把交付源码写坏。现在开头硬断言它等于冻结基准。
2. **制表符账目要按内容比, 不能按行号比**。Pass 0 把活代码里的 tab 换成 4 空格,
   死代码里的 tab 原样保留; 插入/删除行会让行号漂移, 于是"按行号比"的校验在结构性
   改写之后必然假失败。改成比**内容序列**。
3. **成员访问检查要用词边界**。`.common` 是 `.common0` 的前缀, `str.count` 会把后者
   算进前者 (58 vs 57), 误报成"改名碰到了结构体成员"。改用 `\b` 正则。

**坐标系的第二课**: D11 的教训是"行号必须锚在原始文件"。本条又踩了一次同类的坑 ——
`lit_cur()` 的签名必须**在它自己的窗口里唯一**, 而 `'dormantStatus = DORMANT_NO_RESPOND;'`
这类短句在文件里出现两次 (另一处在死代码里)。五处签名都换成了窗口内唯一的写法。

**结果**: 差分 `49,144` 例 0 不一致; 目标端符号集 **115 个完全一致**、0 新增告警、
`.text` 3264 → 3259; 负向对照 **162/162**; `-o2`/`-o3` 反汇编**逐行相同** (各 3146 行) ——
与 `f_vf` / `f_frqSrc` 同类, 是比"允许不同"更强的结果。

**代价 (必须知情)**: 五条既有缺陷与测试台的绕法见
`tools/difftest/cases/f_runSrc/README.md` 第 6 节; 三条测试台自身的洞、两条等价变异、
以及一个**改写引入的真 bug 被测试台拦下**的经过, 见同文件第 8 节。

### D13 — 第三个语义改写模块: `f_frqSrc_pid.c`, 以及"负向对照必须真跑一遍"这条硬规则

**背景**: D11 (`f_frqSrc.c`) 与 D12 (`f_runSrc.c`) 把"替换表驱动改写"这条路走稳了。
本条把它套到 `f_frqSrc_pid.c` (597 行, 4 个活函数, 6 段死代码)。规模比前两个小,
但踩到的坑是**方法论级别**的, 所以单列一条。

**规模**: 47 组改名 / 322 次出现; 23 个 `PID_*` 宏 (Q 格式、定标系数、千分比…);
4 处结构性改写 (宏表插入、`FrqPidSetDeal` 两处判据上提、`fdb` 钳位改 `GetMin`)。
产物 597 行 / 16804 字节, CRLF、纯 ASCII、无注释。生成器
`build/_rewrite_frqsrcpid.py`。

**与前两个模块不同的两点**:

1. **死代码判定要用条件栈, 不能用区间表**。本文件顶部是**四层** `#if` 塔
   (`F_DEBUG_RAM` / `DEBUG_F_POSITION_CTRL` 各两层), 而且第 28~39 行的
   `#if 0 ... #else ... #endif` 里 **`#else` 支是活的** —— 死代码里套着活代码。
   `live_span` (一个区间) 和"手抄几个 `#if 0` 区间"都表达不了, 于是
   `_rewrite_frqsrcpid.py` 逐行维护条件栈自己算。
2. **先展开制表符再匹配**。原文件第 142/143/430 行用制表符缩进, 不展开的话
   锚点会逐字节失配。展开成空格后交付文件零制表符, 与 `verify_tree.py` 的要求一致。

**核心教训: 注释里写下的规则, 不等于表里遵守了规则。**

该用例条目顶部早就写明"刻意避开四类无效变异", 其中第 (1) 类就是
"只改边界等号而两支写同一个值的等价变异 —— 那种必然 MISSED"。**实际写表时仍然
混进了 11 条**。第一轮 187 条跑完: 176 CAUGHT / **11 MISSED**。

逐条核对后, 11 条**全部**是 `tools/difftest/README.md` 第 8 节的 **(b) 类** ——
在可达状态空间里语义等价, 不是测试台有洞:

* 6 条是**幂等钳位**: 边界上走变异支, 而变异支写回的就是判据自己比对的
  那个值 (`if (deltaD > pidDLimit) deltaD = pidDLimit;` 的 `>` 改成 `>=`),
  于是 `x = x` 与原路径的"什么都不做"等价;
* 2 条是**同值两写法**: `if (Qi >= Qp)` 改成 `>`, 分歧点上真支是 `<< 0`、
  假支是 `>> 0`, 都是恒等 —— 对**任意**输入等价, 比"可达集上等价"更强;
* 3 条是**三段式定标在边界上塌成一段**: `if (Qp >= 16)` 改成 `> 16`,
  而 `Qp == 16` 时大格式的移量恰好是 0, 与小格式算的是同一个式子;
  其中 `Ki2` 那条还要用正整数嵌套整除恒等 (`floor(floor(X/a)/b) == floor(X/(ab))`)
  才能证明。

按 D10 的要求"证明 + 记档 + 排除": 11 条从表里删掉 (编号留空 M046/M049/M077/
M079/M084/M087/M129/M139/M142/M144/M172, 与 `f_frqSrc` 缺 31/92/114、
`f_vf` 缺 20/28 一致), 证明写进 `negative_control.py` 该条目顶部与
`cases/f_frqSrc_pid/README.md` 第 8.2 节。**首轮那份部分账本
`docs/_difftest/_negctl_partial_f_frqSrc_pid.json` (`total=187, caught=176,
pass=False`) 与那 11 份逐变体记录一律保留、不删** —— 它们是"11 条确实等价"
这个结论的**原始观测**; 只留重跑后的"全过"总账会把这条推理过程抹掉
(当时的总账是 `683/683`; 之后每加一个用例就并入全量总账, 到那一轮为止已覆盖 33 个用例,
全量总账是 `3174/3174`), 下次有人再看到编号缺口
就没有依据可查。**留下的规则**:

> 无效变异的把关**不能只靠写注释**。注释会被后来的人 (包括我自己) 读漏。
> 真正的把关是**先把负向对照跑一遍**, 让 MISSED 自己冒出来, 再逐条判定是
> (a) 测试台有洞还是 (b) 变异等价。11 条里 6 条落在 `PidFuncCalc`、
> 4 条落在 `UpdatePidFuncPara` —— 恰好是定标/钳位最密集的两个函数,
> 不是随机分布, 也就是说"看一遍代码就能避开"这个假设本身不成立。

**坐标系的第三课**: 本模块的坑是 `outMax` / `outMin` / `aimValue` / `fdb`
**既是局部量名又是结构成员名**。全局替换会把 `->outMax` 也改掉。修法是加
`(?<![.>])` 前视排除 —— 而抓出这个错的是生成器自带的**成员访问计数校验**
(改名前后的 `.name` / `->name` 出现次数必须相同), 不是人眼。D11 的教训
(行号锚在原始文件)、D12 的教训 (签名要在窗口内唯一) 与本条 (改名要排除成员访问)
构成同一类: **凡是"靠人盯"的校验, 迟早会漏; 能写成计数的就写成计数。**

**结果**: 差分 `21,411` 例 0 不一致; 目标端符号集 **33 个完全一致**、0 新增告警、
`.text` 1707 → 1718 (+11); 负向对照 **176/176**。

**代价 (必须知情)**: 六条既有缺陷与测试台的绕法见
`tools/difftest/cases/f_frqSrc_pid/README.md` 第 6 节。其中缺陷 (f)
(`UpdatePidFuncRefFdb` 在 `default:` 支不赋值却无条件读取 `aimValue`/`fdb`)
是**真缺陷但不可测** —— 两侧是不同函数, 栈帧残值不保证相同, 第一版测试台因此
报过 50 处假警; 驱动把 `pidSetSrc`/`pidFdbSrc` 收窄到功能码表能实际产出的范围
并把它记进 README, 而不是去"修"这个缺陷 (修它就是行为变更)。

**与 D12 的对照**: `f_runSrc` 那一轮是"改写引入的真 bug 被测试台拦下";
这一轮反过来 —— 是**测试台自己的无效变异**被负向对照拦下。两次都是
"先把对照跑完再下结论"救的场。

### D14 — 宿主位宽的"折叠"探针, 以及"CAUGHT 不等于覆盖被钉住"

**背景**: 前 33 个模块的差分测试台都建在一处不一致上 —— 宿主 `int` 是 32 位,
目标 C28x 的 `int` 是 16 位。轮到 `MotorInvProtect.c` (第 34 个) 时, 这一处不一致
第一次**同时朝两个方向**露头: 变体 `L28` (`m_LDeta >= cap` 的等号) 在宿主上被判
"等价", 而逐条推演后在目标上**也确实是等价的**(证明见
`build/_me_equiv_motorinvprotect.log`); 变体 `P33` (`if(pid->Deta > 0)` 的等号)
在宿主上却"抓不到", 补了驱动才抓到。两件事并排看, 结论只能是:
**宿主的位宽不是可以忽略的噪声, 它是另一套算术语义**, 必须显式对齐。

**决定 (折叠)**: 在用例自己的 `shim/DSP2803x_Device.h` 末尾加 `#define int short`,
让模块里的 `int` / `Uint` / `Uint16` 与目标的 16 位同宽。词法上躲不掉的 `long int`
(`include/motor/SubPrgInclude.h`) 折叠成 `long short` 会编译不过, 于是在该用例的
`host_patch.json` 里改写成 `long` (2 处, 两侧都改)。驱动再加一条**运行期宽度断言**
(`sizeof(Uint)==2 && sizeof(int)==2 && sizeof(long)==4`), 位宽一漂就当场 `rc != 0`。
此前对 `#define` 类改动的口径是"能不用就不用"; 这一次的判据是**在逐模块用例里,
对齐位宽比不对齐更忠实** —— 不对齐, 测试台就在一套目标上并不存在的语义里下判断。

**残留差异 (必须知情)**: 折叠之后 `unsigned short - unsigned short` 仍按 C 的整型提升
在 **32 位 `int`** 里算, 而 C28x 上是 16 位无符号环绕。写驱动时这是硬约束: 探针不能把
"只在 16 位环绕下成立"的状态当成观测点 (两侧会因为宿主不环绕而同时"看不见"),
这类位宽相关行为只能靠目标端检查与人工审查兜住 (见第 4 节第 7 条)。

**核心教训: "CAUGHT" 不等于"覆盖被钉住了"。** 负控全量跑完 (157 条) 后又冒出 2 条
MISSED (`T06`/`T09`, 都落在温度表选择), 而它们**首轮是 CAUGHT 的**。追下去是两层原因:
(1) 表选择的结果只经 `if(mType - TempBak >= 8)` 这道刷新闸写出去; (2) 驱动把
`TempAD`/`TempBak` 都按**原始 ADC 刻度**戳, 于是刷新在宿主上永远不触发
(`code - 32768` 为负), 变体换了另一张表却仍写出逐字节相同的全局量。首轮能抓到,
靠的是随机相撞上一组 `TempBak` 小的输入 —— 也就是说, **那条 CAUGHT 从来没有被任何
构造场景支撑**, 它跟着驱动取样走, 驱动一改就掉。

> 留下的规则: 一条变异的证据强度, 取决于它是被**构造出来的场景**抓到的, 还是被
> `random` 相撞上的 —— 两者在总账里长得一模一样。所以要能逐条倒查: 每条变异的落盘
> 记录 stdout 里有 `MISMATCH <tag>`, `tag` 是场景名; 全是 `random` 就说明它没被钉住。
> `build/_me_phase_audit.py` 就是干这个的, 任何用例都能跑。

按这条规则把本模块 157 条过了一遍: 只有 `F08` (`gFanCtrl.RunCnt++` → `+= 2`) 只由
random 相抓到 —— 因为 `phase_fan` 当时只戳 `RunCnt ∈ {4999, 5000, 5001}`, 这三个值
都会被 `if(RunCnt >= 5000)` 钳回 5000, 增量差异被钳位吃掉; 补上 `{0, 1, 4997, 4998}`
后由 `fan` 相直接抓到。现在本模块 **157/157 都由确定性场景抓到**。同一审计在当时
全工程 `3174` 条记录 (33 个既有用例, 不含本轮这 157 条; 主账现为 3587 条) 里发现
**430 条 (13%) 只由 random 相抓到** —— 那是 33 个既有用例的既有
性质 (阳性差分在同一 `nrand` 下仍可复现, 只是覆盖没钉在具名场景上), 不在本轮改动
范围内, 已记进 `rewritten_modules.json` 的 `coverage_gaps`, 留给后续收紧。

**等价变异的删除要用加强后的测试台复测**: 本模块删掉 6 条可证等价变异
(`T12`/`T14`/`T16`/`L19`/`L28`/`L31`) 之后驱动又变强了 (加了码值尺度探针)。

### D15 — 第一个"不拥有任何全局量"的模块: 测试台反过来由**共享镜像**定义, 以及"告警集合"这条真门禁

**背景**: `MotorMain.c` 是 2ms / 载波 / ADC 中断的任务层 (15 个入口, 1390 字), 它把整个
驱动器的状态写进**别的模块**的全局量。`nm2000` 给出的符号表里只有 15 个 `T` (函数),
一个 `D`/`B` 都没有 —— 这个模块**没有私有状态**。

**决定 (测试台形状)**: 前 34 个用例的骨架是"共享镜像 + 每侧私有镜像", 两侧各持自己那份
模块私有全局量逐字段比。这里没有私有镜像可同步, 骨架退化成: 保存输入镜像 → 调 ref →
快照 S_ref → **恢复输入镜像** → 调 new → 快照 S_new → 逐字节比。恢复这一步是关键:
少了它, ref 的写入会漏进 new 的输入, 把差异洗掉。又因为被调函数是**共享**的 (同一份内存),
"改写把某个调用删掉 / 挪走 / 重复"可能完全不在全局量上留痕 —— 于是 73 个被调函数全部
实现成**计数桩**, 计数器 `gMockCall[]` 与 `gHostCpuCtl[7]` (`DINT`/`EINT`) 一样进比对镜像。
调用序也是证据, 不只是数值。

**教训 1: 目标端告警集合是硬门禁, 它会约束"哪些名字能动"。**
改写时把一个**只写不读**的局部量 `m20HzPu` 顺手改了名, `target_check.py` 当场
`pass: false`: 老名字与新名字各带一条 `variable ... was set but never used`, 于是
`warn_added` / `warn_gone` 都非空。这不是门禁太严 —— 编译日志也是产物, "外部可观测性"
本来就包含它。结论: 死变量的**名字**在告警里是可观测的, 不是自由变量。
这与 D10 的"记录不作门禁"不冲突: `.text` 尺寸是记录, 告警集合是门禁。

**教训 2: 有的变异会污染工具链, 不能留。**
两条变异 (`R01`/`X09`) 让 `RunCaseRun2Ms` 与 `RunCaseStop` 的停机 / 启动判据互为反面,
两侧互相递归 → 栈溢出。它"抓到"了 (`rc != 0`), 但只有崩溃码、没有字段级证据, 而且崩溃
进程变成不可回收的僵尸、占着变体 exe 的文件名, 下一次编译直接 `LNK1104`, 把**后面的**
变异记成 BROKEN。按 D11 的口径 (崩溃型 CAUGHT 可以接受, 如 MotorInvProtect 的 `AN1`),
这里仍然**替换掉**它: 同一判据恒不成立的等价写法 (`== 2` 落在 1 位字段上) 能拿到字段级
差异 (`R24`/`X21`)。留下的是"证据更强的那一条", 不是"更刺激的那一条"。

**教训 3: 相位审计第二次当真。**
256 条里有 1 条 (`Q16`, `RUN_SYNC_TUNE` 的 `PM_EST_WITH_LOAD` 支) 只由 `random` 相撞到。
补法是**追加** 4 个确定性场景 (对 `ParEstContent[0]` 取 4 个 `TUNE_STEP_NOW` 值) 到既有
`phase_adcover` 的末尾 —— 追加而不是插入, 因为 `random` 相用独立种子, 追加不会移动
随机流, 于是**已有记录不失效** (`cases` 22487 → 22517)。改完 driver 后本模块 0 条
random-only。

**结果**: 差分 `22,517` 例 0 不一致 (15 个入口的构造场景 + 20000 例随机); 目标端
`pass: true`、0 新增告警、导出符号集合完全一致、`.text` 1532 → 1525 (−7, 记录不作门禁);
负向对照 **256/256** (主账 3,587/3,587); 3 条证明为等价的变异按 D14 的做法删除留空
(`B24`/`B39`/`Q05`), 证明见 `build/_me_equiv_motormain.md`。

### D16 — 第一个"整体不可达"的模块: `f_debug.c`, 证据降级为函数级并写明

`f_debug.c` 是第一个**在出厂固件里根本不会被调用**的模块。查清这件事花的时间比
改写本身多, 但它是"这条证据到底证明了什么"的分界线, 所以先查。

三条证据, 缺一不可:

1. **宏配置**: `include/function/f_debug.h` 里 `DEBUG_F_POSITION_CTRL` 在
   `#if !defined(ZJ_MD380M)` 时取 0。而 `ZJ_MD380M` **任何构建配置都没有定义** ——
   两个 `.lkf` 里连一个 `-D` / `--define` 都没有, 真正生效的宏只有
   `tools/build_and_compare.py:44` 的 `-d_DEBUG -dDSP2803X -dLARGE_MODEL`。
2. **唯一调用点**: 全工程只有 `f_runSrc.c:928-936` 的 `UniversalDebug(0..5)`,
   整块在 `#if DEBUG_F_POSITION_CTRL` 里。
3. **目标文件实证**: `nm2000 build/Debug/f_runSrc.obj` 的**未定义符号里没有**
   `_UniversalDebug`。调用点确实没编译进去。

第 3 条是关键。前两条只是"读宏推出来的", 而宏的正确读法依赖预处理器的实际行为;
第 3 条是从编译产物直接读的, 不依赖任何推理。**宏能骗人, 目标文件不能。**

由此定下两条规矩:

* **证据等级要写明, 不能含糊**。"函数语义等价"与"被主循环调用到时行为正确"
  是两件事。本模块的差分测试证明前者; 后者在出厂配置下是空的 (没有调用点),
  所以不证。将来若打开 `ZJ_MD380M`, 可达性变了而函数语义没变, 本用例的结论
  仍然有效 —— 这一点写进 `rewritten_modules.json` 的 `coverage_gaps`。
* **空体函数不进变异清单**。九个入口里八个的函数体整块在 `#if 0` 里, 目标端各自
  只编出一条 `LRETR`。改那里的任何东西都不产生行为差异 —— 那是可证明的等价变异,
  留着只会让总账永远差几条。它们由差分测试的 `phase_empty` 覆盖 (调用、断言状态
  不动、断言两侧一致), 不由变异覆盖。

顺带记一个必须知道的代码生成事实: `InitDebug` 的函数体是三次对空体函数的调用,
cl2000 **在 -O0 下也会把这三条调用整个删掉**, 实测 `_InitDebug` 只有 1 个字
(一条 `LRETR`)。改写时若把那三次调用换成加参数 / 加判断的写法, 它就会变成多字,
Tier A 立刻不等 —— 而这种"改动看着无害"的地方正是最容易漏的。

**结果**: 差分 `150,226` 例 0 不一致, 覆盖跑满
(`guard=13 idle=32768 edge=15 store=32985 storeMiss=264 wrap=32985 wrapMiss=0`);
目标端 `ref/new rc=0`、0 告警、30 个外部符号完全一致、`.text` 162 → 120;
负向对照 **34/34** (主账 4,073/4,073), 其中 1 条 (`DBG31`) 首轮 MISSED、
证明为等价后按 D14 **删除** (证明: 该语句在 `scopeIndex < scopeNum == 1` 里面,
下标恒为 0)。

### D17 — 纯数据模块不改写: `MotorConstant.c` / `MotorVar.c` / `DSP2803x_GlobalVariableDefs.c` / `f_funcCode.c`

这四个模块里**没有函数**, 只有 `Uint const ... [N] = {...}` 的标定表、变量定义和
外设寄存器定义。它们不进改写清单, 理由是"改写"在这里没有意义而不是"来不及":

* 表里的**数字就是规格**。任何改动都改变行为 (死区补偿量、反电势表、电流标定表),
  所以数字不能动。
* 结构上也没有可变的余地: 拆表会改外部符号集, 合表会改数组长度, 加 `static` 会
  改链接属性 —— 三种都改变链接结果, 不是"实现变化"。
* 因此它们的等价性由**最强的那一层**保证: 目标文件与原工程**逐字节相同**
  (Tier B)。这比任何改写后的行为等价都强, 也正是契约里"没改写过的必须相同"的
  字面要求。

`MotorConstant.c` 623 行、15 个 `const` 数组、0 个函数 —— 这个形状本身就说明了
为什么它属于这一类。

**`f_funcCode.c` 是第四个, 也是最极端的一个**: 原文件 1360 行 / 112023 字节,
交付版 1232 行 / 85945 字节, 全文**零个函数**、零条语句, 只有

|---|---|---|
| `FUNCCODE_ALL funcCode;` | 1 个定义 | 功能码全局量 (EEPROM 镜像, `F_DEBUG_RAM` 时放 `data_ram`) |
| `funcCodeGradeCurMenuMode[FUNCCODE_GROUP_NUM]` | 83 项 | 当前菜单模式下各组可访问的最高 grade |
| `const funcCodeGradeAll[FUNCCODE_GROUP_NUM]` | 83 项 | 各组 grade 总数 (`F0NUM - 0` 这类) |
| `const funcCodeGradeSum[FUNCCODE_GROUP_NUM]` | 83 项 | 各组起始 index, 由 `GetCodeIndex(funcCode.group.xx[0])` 宏算出 |

所有"函数" (`GetCodeIndex` / `GetGradeIndex` / `FACTORY_PWD_INDEX` …) 都是

`.text` 段**、`build_and_compare.py` 把它归进"纯数据(不适用)"的原因。交付版目标文件

$build.attributes                     42      .debug_info      20462
.text                                  0      .debug_abbrev      218
.data                                  0      .econst:_fcNoAttri2Eeprom          104

`.text` / `.data` / `.bss` 三个段**长度都是 0**, 全部载荷是 `.econst` 与 `.ebss`
的初始化数据 —— 没有一条指令。

这里**一个字都不能改**: `funcCodeAttribute[]` 的 911 行就是整机的参数规格
(上下限、默认值、属性位、EEPROM 地址), 改一个数字就改了机器行为, 改一行顺序
就把所有参数搬到别的 EEPROM 地址上。所以它走的是同一套最强证据:

* Tier A (反汇编) 相同 —— 它没有 `.text`, 比较的是段表与符号表;

所以它是**编译期常量**, 这张表落在 `.econst` 且**零重定位** (实测 `nreloc 0`),
不是 `.cinit` 里的动态初始化。"把 83 行改写成循环生成"在这里也是错的, 理由不是
风格而是链接: 该符号在头文件里声明为 `extern const Uint16 funcCodeGradeSum[]`
(`f_funcCode.h:1523`), 被 5 个模块的 8 处 `GetGradeIndex` 直接索引

`f_profibus.c:321,440,443`)。改成运行期生成就得把它变成可变全局量、再加一个初始化
函数, 并保证它在上面 8 处之前被调用 —— 那是**新增外部符号 + 新增启动顺序约束**,
属于功能与链接层面的改动, 不是"实现适当变一下"。

### D18 — "被覆盖的写"不等于"可删的写": `InitSetSciDp` 的 SWRESET 时序, 以及测试台覆盖边界的写法

`f_comm_DP.c` 的 `InitSetSciDp` 在 `NO_FIFO == 1` 分支下写了七次寄存器, 其中
`SCICTL1` / `SCICTL2` / `SCICCR` **各被写两次**:

```c
p->pSciRegs->SCICTL1.all = 0x0001;   /* <-- 被下面的 0x0023 覆盖 */
p->pSciRegs->SCICTL2.all = 0x00C2;   /* <-- 被 0x00C3 覆盖 */
p->pSciRegs->SCICCR.all  = 0x0087;   /* <-- 被 0x0087 覆盖 (值相同) */
p->pSciRegs->SCIPRI.bit.FREE = 1;
p->pSciRegs->SCICTL1.all = 0x0023;
p->pSciRegs->SCICTL2.all = 0x00C3;
p->pSciRegs->SCICCR.all  = 0x0087;
```

从**宿主测试台**看, 前三次写完全不可观测 —— `SciaRegs` 只是一块内存, 两次写之后
读到的都是后写的值。于是三条诱惑同时出现: 删掉前三次 (代码更短)、把三次合并
(看起来是"消冗余")、或者造一条"删掉前三次"的变异并期望它 CAUGHT。

**三条都错**, 理由是硬件语义: `SCICTL1 = 0x0001` 的 bit0 是 `SWRESET`, 写它会
把 SCI 状态机复位、丢弃收发缓冲; 紧接着 `0x0023` 释放复位并配置。这是"先复位再
配置"的**时序**, 不是冗余赋值。删掉它, 宿主测试照样全绿, 真机上却可能带着上一次
运行的残留状态进初始化。

由此定下两条规则:

1. **凡是"值被覆盖但副作用在真机上存在"的写, 一律保留原样**, 不做合并、不做删除,
   也不为它造变异 (变异在宿主上不可观测, 只会产生假 MISSED 或假 CAUGHT)。
2. **这种情况必须写进 `coverage_gaps`, 措辞是"测试台覆盖边界", 不是"等价性声明"**。
   区别在于: "等价性声明"说的是"我证明了两种写法一样"; "覆盖边界"说的是"这一段
   我的证据够不到, 所以我一个字符都没动, 请你按源码审查"。前者一旦说错就是假的
   保证, 后者是可核查的诚实。

同一形状的还有 `#define FIFO_NUM  16;` 的尾分号: 它只在 `NO_FIFO == 1` 时才能
编译 (那时 `FIFO_NUM` 只出现在被编掉的 `#else` 臂里, 从不展开)。一旦有人把
`NO_FIFO` 改成 0, `for (i = 0; i < FIFO_NUM; i++)` 会展开成 `i < 16;; i++` 而
编不过。改它等于改配置阶梯的语义, 所以也不动, 只记录。

### D19 — 在 16 位截断点上, 改写只能动**结构**, 不能动**表达式**

`MotorPmsmMain.c` 是第一个"几乎全是 16 位算术"的模块: C28x 上 `int` 16 位、
`long` 32 位, 而模块里到处是"先升位、算完再截断回 16 位"的写法。典型:

```c
m_Pos = (mCntMod<<14)/(int)gPGData.PulseNum;   /* m_Pos 是 int, 商在赋值处截断 */
gIPMZero.FeedPos = m_Pos * gMotorExtInfo.Poles;
```

如果改写时"顺手"把中间量留在 `long` 里 (例如把两行合成
`gIPMZero.FeedPos = (mCntMod<<14)/(int)PulseNum * Poles;`), 结果会在
`mCntMod` 较大时分叉 —— 而且只在少数输入上分叉, 差分测试的随机相根本踩不到。

同理这一对**不能**合并:

```c
m_CoffA = m_CoffA>>1;
m_CoffB = m_CoffB>>1;
gIPMPos.Ld = m_CoffA - m_CoffB;      /* 两次截断各丢一次余数 */
```

写成 `Ld = (m_CoffA - m_CoffB)>>1` 少丢一次余数, 于是"更正确"了, 也就不等价了。

**结论 (本模块的改写边界)**: 算术表达式逐字符保留, 只改控制流、语句分组、
局部变量作用域和辅助函数抽取。9 个差异块全部属于这四类。这不是保守, 是
"能证明的部分才动" —— 一个表达式的等价性要按 16/32 位截断点逐个论证, 而一个
`if/else` 改早退的等价性是显然的。

### D20 — 观测路径上的**乘法**和**滤波**会把要找的差异精确抵消

负向对照首轮 12 条 MISSED 里有 4 条不是"测试台覆盖不到", 而是**观测路径自己
把差异抹平了**。两种形状, 都值得记:

**(1) 乘一个 2 的幂, 差异归零。** `m_4Pluse` 从 `PulseNum<<2` 改成 `PulseNum<<1`,
角度恰好差 **32768**。而角度链末尾是

```c
gIPMZero.FeedABZPos = m_ABZPos * gMotorExtInfo.Poles;   /* FeedABZPos 是 16 位 */
```

`Poles = 4` 时 `32768 * 4 = 131072 ≡ 0 (mod 65536)` —— 差异**正好**被抹掉。
所以"极对数"不是装饰, 是输入: 必须含**奇数**, 因为 `32768 * 奇数 ≡ 32768`。

**(2) 一阶滤波把"差 1"抹平。** `frq` 的取值差 1 之后要过 `Filter4`:

```
Filter4(x,total) = ((total<<16) + (x<<14) - (total<<14)) >> 16   /* 无符号 32 位 */
                 = (3*total + x)/4
total = 10 : (30+5)/4 = 8,  (30+4)/4 = 8      <- 一样
total =  9 : (27+5)/4 = 8,  (27+4)/4 = 7      <- 不一样
```

默认输入给的正是 10。**必须扫滤波器的前值**, 而且只有 `total ≡ 1 (mod 4)` 才
分得开。

**结论**: 当被测量要经过"乘法 / 除法 / 滤波 / 钳位"才到达比较点时, 那条路径上的
每个参数都是**输入**, 不能钉死。判断方法很简单 —— 问一句"这个差异到了比较点还是
同一个数吗", 而不是"这个差异产生了吗"。

### D21 — 锚点审计的判据不能"宁可错杀": 门禁常年报红等于没有门禁

`build/_audit_anchors.py` 的判据 B 原来写成"语句形锚点命中行中间就报违规"
(`prefix.strip() != ''`)。全库跑出来 3 条违规, 逐条核对后**三条都是正确锚点**
(`src.count(anchor) == 1`, 命中行就是想去的那一行):

```
MotorInvProtect C07   \telse\t\t\t\t<锚点>          前面是 else + 制表符
MotorMain IN18/IN20      gFVCSpeed.<锚点>            锚点是成员访问的尾部
```

这两类都是**正确**的行中命中: 语句确实从锚点处开始, 替换后得到的正是想要的语句。
误报的代价不是"多看一眼" —— 门禁常年报红, 真正的那一条就淹在噪声里。

所以 B 收窄到它**能证明**的那一种形状: 命中处前面**只剩一个类型关键字**, 说明锚点
其实是某条**声明的初始化式** (FM136 的形状: 打在文件作用域初始化式上, 而初始化式
每次调用前都被 driver 覆盖 = 等于没打)。"作者是不是选错了语句"这个问题 B 不再
假装能判断, 交给 `dups()` (两条变异产生同一份源码) 和 `--multi` 的人工复核。

配套要求: 判据改了必须有**自测**。`build/_audit_selftest.py` 合成一份 FM136 / FM42
形状的源码必须报违规, 上面三条真实形状必须不报。没有自测的"放宽判据"和"关掉判据"
在结果上分不开。

### D22 — 相位审计的两处硬伤: 标签名是**字符串契约**, 正则不能跨行

`build/_me_phase_audit.py` 判"这条变异是被人写的场景钉住的, 还是被随机相位撞上的",
靠的是记录里 `MISMATCH <tag>:` 的标签。这个判据有两处会**静默失效**:

1. **跨行正则**。原式 `^MISMATCH ([^:]+):` 里的 `[^:]` 把换行也算进去了。若某条
   `MISMATCH` 自身的文本里没有冒号 (例如 `MISMATCH op=ZeroPosControl`), 模式就一路
   吞到后面第一个冒号为止, 于是"标签"变成 `'op=ZeroPosControl\n  ref=...'` 这样的
   多行碎片。碎片既不等于任何场景名, 也永远不可能匹配随机标签 —— **判据被绕过**,
   而输出里看不出来 (它只是把标签打印得难看)。改成 `^MISMATCH ([^:\n]+):` 并
   `.strip()`。修正后全库"只由随机相位抓到"的数字由 `439` 变成 **`695`** ——
   此前那个数偏低, 低在标签被读错上。
2. **标签名写死成 `random`**。`MotorPmsmParEst` 的随机相位原先打印 `rand`, 而审计
   只把 `random` 当非确定性标签, 于是**对本用例天然失明**: 每条记录看起来都被
   "确定性场景"抓到, 报出 0 条 fragile, 什么也没证明。这是"门禁常年报绿"的版本,
   比报红更糟 —— 报红至少有人去查。修法与 D21 同源: 把标签**声明化**。

于是审计增加了 `RANDOM_PREFIX` 表 (按用例声明随机相位的标签前缀, 因为有的驱动把
标签格式化, 例如 `random[%u]` / `rnd-zero` / `rand-deal` / `random BAUD`), 并且:

* 逐用例打印它据以判定的标签前缀, **默认规则的用例数**也要打印 —— 声明错了当场
  可见, 而不是变成一条没人注意的更松的判据;
* 对每条记录检查标签是否"可解释" (随机前缀, 或能在该用例 `driver.c` 的字面量/
  格式化前缀里找到), 找不到的标签逐条列出; `--strict` 下非零退出;
* 随机相位之外的标签仍按"手写场景"计, 所以**要求每条变异至少被一个手写场景抓到**
  这条门禁的方向没变。

**留下的局限 (必须明说)**: 43 个用例里只有 6 个声明了非默认的随机标签, 其余 37 个
仍走 `random` 默认规则。因此 `695/4572` 这个数是**下界** —— 标签写法与 `random` 不同
的用例会把 random-only 少算。审计输出里已把这一行标注成 `LOWER BOUND` 并给出仍走
默认规则的用例数。彻底的做法是逐个用例读驱动、把随机标签补进表里 (一次几十行的
机械修改), 留给后续收紧; 本轮的三个重点用例 (`MotorInvProtect` / `MotorMain` /
`MotorPmsmParEst`) 的随机标签都是 `random`, 它们的 `0 条 random-only` **不受此局限
影响**。另有约 211 处标签在当前判据下"不可解释" (主要是驱动用 `printf` 拼出来的
标签), 已逐条打印而不是丢弃。

### D23 — 两种新的"全域等价"形状: 对称差, 与同一次调用内的幂等寄存器写

`MotorPmsmParEst` 首轮 10 条 MISSED, 其中 8 条是测试台的洞 (见 D20 的同类), 2 条是
**全域等价** —— 按 D10 的纪律"证明 + 记档 + **删除**清单项 (编号留空)", 不保留成
"MISSED 但已解释", 因为 `test_difftest_negctl.py` 的期望集合是从清单推出来的, 留一条
等价的只会让期望集合永远差一条。

* **对称差**: `m_Cur = m_Cur - gIPMInitPos.CurFirst;` 改成 `CurFirst - m_Cur`。该赋值
  之后 `m_Cur` 在这个分支里**唯一的去处**是 `abs(m_Cur)`, 而 `abs(a-b) == abs(b-a)`
  在补码下对任意宽度的 `a`/`b` 恒成立 (含 `x - c == INT_MIN` 这个角落: 两种写法都
  得到 `INT_MIN`)。判据是"差异到了比较点还是不是同一个数" (D20) —— 这里连数都不是,
  是同一个**函数值**。
* **同一次调用内的幂等寄存器写**: `SynInitPosDetect` 的 `case 5` 第一行已无条件
  `DisableDrive()` (即 `GpioDataRegs.GPASET.bit.GPIO7 = 1`, 置位型寄存器), 到变异
  那一行之间没有任何 `EnableDrive()`, 所以到达时该位已是 1; 删掉 else 分支里的第二处
  `DisableDrive()` 对寄存器状态**没有任何可观测影响**。注意这不是"覆盖不到":
  驱动确实走到了那个 else 分支 (`det_s5e` 计数器非零), 是那条语句本身冗余。

两条都记在 `build/_me_equiv_pmsmparest_negctl.md`, 清单由 221 条变成 219 条。
